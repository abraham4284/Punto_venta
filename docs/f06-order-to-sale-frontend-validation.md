## Implementacion

- [OrderDetailPage](../client/src/views/businesses-app/module/orders/page/OrderDetailPage.tsx) ofrece Convertir a venta solo READY con orders.convert **y** sales.create. Label de permiso agregado; no hay grants frontend nuevos. COMPLETED conserva sin editar/cancelar/status/conversion.
- [OrderConversionDialog](../client/src/views/businesses-app/module/orders/components/OrderConversionDialog.tsx) usa Dialog Base UI con scroll interno y footer separado. Resumen read-only de numero, cliente, deposito, modalidad, productos/cantidades, subtotal, descuentos, entrega y total; destinatario/telefono/direccion/referencia DELIVERY tambien read-only. Solo admite pagos y metadata complementaria, no edicion del pedido ni una segunda pantalla POS.
- Caja reutiliza useSaleCashSession. Muestra nombre/abierta, carga/error/ausente y boton de actualizar; sin caja no habilita confirmar. cash.view habilita enlace a /admin/cash en otra pestana. No abre/cierra caja desde checkout.
- Reutiliza usePaymentMethods, SalePaymentInput y SalePaymentsSection. Seleccion inicial: esperado activo -> default activo -> primer activo; si ninguno, sin ID inventado. Importe inicial = total Order; PICKUP confirmado, DELIVERY pendiente. No se crea un pago automaticamente por el campo esperado: el usuario confirma los pagos configurados.
- 1..5 pagos con metodo/importe/estado/referencia/observacion, suma Decimal exacta contra Order.total, total/asignado/restante. No confirma desbalance, metodo no disponible o sin caja. PICKUP solo CONFIRMED; DELIVERY PENDING/CONFIRMED. Pequeno ajuste compartido en SalePaymentsSection: disabled del configurador, limite cinco, labels/IDs/aria y errores asociados, referencia 100/observacion 255 segun Sales; preserva el flujo POS existente.
- DELIVERY permite cadete, fecha/hora local convertida a ISO y observacion opcionales. Reutiliza getDeliveryUsersForSaleRequest y OrderSelect/Base UI. Cadetes son opcionales; fallo de carga se informa y permite continuar sin asignar. PICKUP envia delivery null y no muestra metadata de reparto.
- [Tipos/API Orders](../client/src/views/businesses-app/module/orders/types/orders.types.ts) agregan linkedSale y contrato reducido. Se reutiliza SaleWithDetailsResponse/contrato de pagos y se agregan idOrder/deliveryFee al tipo SaleResponse para reflejar F5. OrderSummary omite linkedSale porque el listado no lo devuelve. El request tipado usa exclusivamente Axios BUSINESS y POST /orders/:id/convert-to-sale con UUID Idempotency-Key; body solo idCashSession, payments y delivery metadata/null.
- [useOrderConversion](../client/src/views/businesses-app/module/orders/hooks/useOrderConversion.ts) mantiene formulario local y errores, con useForm para metadata. Zod valida campos de pago/metadata; no recalcula precios, cantidades ni total del pedido. Key/fingerprint estable por intento con helper existente; cambios en caja, pagos o metadata invalidan key, exito/replay la limpia. Mutex bloquea doble click y edicion/cierre durante submit. Error conserva campos y checkout abierto.
- Mensajes seguros para reglas F5, caja/metodos/cadete/stock/403/404 y concurrencia. Ante 409 se consulta Order antes de reintento; si falla refresh, queda bloqueado con accion explicita de actualizar. Un estado actualizado distinto de READY conserva el formulario pero bloquea conversion.
- Exito/replay aplica response.order, cierra checkout, muestra toast y recarga detalle/eventos. [OrderLinkedSale](../client/src/views/businesses-app/module/orders/components/OrderLinkedSale.tsx) muestra venta/estado; sales.view habilita /admin/sales/:idSale. Sale CANCELLED muestra Venta vinculada anulada, Order sigue COMPLETED y sin reconversion. No fuerza estados economicamente desde frontend.
